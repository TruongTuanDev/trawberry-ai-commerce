# i18n

## Role policy

- Admin:
  - supported locales: `en`
  - default locale: `en`
  - no language switcher
- Seller:
  - supported locales: `ru`, `en`, `vi`
  - default locale: `ru`
  - language switcher visible in Seller Center
- Public / customer:
  - supported locales: `ru`, `en`
  - default locale: `ru`
  - language switcher visible in public surfaces

## Resolution order

1. logged-in user `preferredLocale`
2. locale cookie
3. role default

Current phase intentionally does not let browser language override the public default Russian fallback.

## Seller center status

Seller operations now support localized navigation and core operational copy for:

- shell navigation
- products list and product status/action labels
- orders tabs and order actions
- payment review queue and payment detail
- notifications heading and empty/filter states

Seller payment settings and product filtering now also live-switch correctly in `ru`, `en`, and `vi` without a page reload:

- `/seller/payment-settings`
- `/seller/products` filter/search toolbar
- seller shop switcher chrome
- seller product editor visibility metadata form

Seller direct routes now hydrate without relying on a preselected `currentShopId`:

- `/seller/orders/[id]`
- `/seller/payments/[orderId]`
- `/seller/products/[id]`
- `/seller/products/[id]/images`
- `/seller/orders`
- `/seller/payments`

The frontend resolves the needed shop context from seller-accessible detail APIs, then syncs the workspace store after the detail payload loads.

## Customer account status

Customer-facing account surfaces now support localized `ru` and `en` copy for:

- customer login and register
- customer account shell navigation
- dashboard, profile, addresses, security, and support pages
- customer order history and order detail
- customer return / refund pages
- customer-facing notification headings and filters
- customer notifications shell header/subtitle with live RU/EN switching
- customer returns/refunds form, detail timeline, and custom file-picker copy
- customer support and receipt lookup labels inside order-detail and receipt flows

Buyer-facing UI must not expose Vietnamese:

- public header switcher shows only `RU` and `EN`
- customer auth and account pages show only `RU` and `EN`
- customer-specific dictionaries are maintained in `en.json` and `ru.json`

## Public shop profile status

Public shop profiles now use buyer-facing RU/EN copy for:

- shop hero title/metadata
- verified badge
- product count and rating placeholder
- joined date
- message-shop placeholder CTA
- back-to-catalog CTA
- public shop product section title
- public shop search and sort controls
- empty and not-found states

Buyer/public locale policy remains unchanged on the new route:

- supported locales: `ru`, `en`
- default locale: `ru`
- no Vietnamese option in public shop UI

## Product reviews status

Verified product reviews now add localized review UI across all supported role surfaces:

- public/customer RU/EN:
  - public product review section
  - rating summary labels
  - verified purchase badge
  - write/edit review flow in customer order detail
  - custom localized review photo picker
  - localized review validation and stable review error-code mapping
- seller RU/EN/VI:
  - seller reviews page
  - customer photo labels and empty-image state
  - reply action and review status labels
- admin EN:
  - basic review moderation list
  - hide / restore review actions

## Messaging status

Buyer-seller messaging now adds localized messaging UI across supported role surfaces:

- public/customer RU/EN:
  - `Message shop` entry points on public shop profile and product detail
  - customer message thread list and detail
  - new-message composer
  - report-thread and closed-thread states
  - localized stable message error-code mapping
- seller RU/EN/VI:
  - seller messages list and detail
  - reply composer
  - unread/open/closed/reported filters
- admin EN:
  - reported thread review list
  - close / reopen actions

Buyer locale policy remains unchanged on messaging surfaces:

- supported locales: `ru`, `en`
- default locale: `ru`
- no Vietnamese option in public/customer messaging UI

Buyer locale policy remains unchanged for reviews:

- supported locales: `ru`, `en`
- default locale: `ru`
- no `vi` exposure in review UI on public/customer surfaces

Review photo upload rules:

- up to `5` photos per review
- `JPG`, `PNG`, `WEBP` only
- `5 MB` max per image
- no video upload yet
- hidden reviews hide their public photos too

Business regressions should not assert translated copy. Customer E2E contracts now prefer:

- `data-testid`
- raw `data-status`
- route or visibility outcomes

## Customer cleanup audit

- Buyer/customer UI remains `ru` and `en` only.
- Customer notifications shell no longer contains Vietnamese hard-coded text.
- Customer returns/refunds no longer depend on browser-native file input labels; the UI now uses a localized custom trigger and filename state.
- Customer receipt and support sections now subscribe to live customer locale state instead of mixing static English labels into RU sessions.

## Error and toast localization

Frontend maps stable error codes instead of translating backend free-text strings. Current shared mappings include:

- `CUSTOMER_ADDRESS_REQUIRED`
- `CUSTOMER_ADDRESS_NOT_YANDEX_READY`
- `SHOP_PAYMENT_METHOD_NOT_SUPPORTED`
- `UNAUTHORIZED`
- `FORBIDDEN`
- `VALIDATION_ERROR`
- `OUT_OF_STOCK`
- `PRODUCT_NOT_AVAILABLE`

## Remaining gaps

- seller finance, returns, delivery detail, and some AI/workbench screens still contain legacy hard-coded copy outside the current migration scope
- some older shared flows still need contract hardening from localized text assertions to `data-testid` or raw status assertions

## Locale switcher redesign

- seller and buyer/customer surfaces now use one shared locale switcher component with a central locale metadata map
- each dropdown item shows flag, short code, native language name, and active check state
- seller switcher supports `RU / EN / VI`
- public and customer switchers support `RU / EN` only
- live switching stays client-side and immediate, while preferred locale persistence still uses the existing cookie plus `/api/users/locale` flow
